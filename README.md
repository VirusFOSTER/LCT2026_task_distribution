# LCT2026_task_distribution
## Краткое описание
Данный проект предназначен для решения VRP-задачи.

### Постановка задачи
Дано:
    1) N исполнителей задач (пусть это будут инженеры)
    2) M задач на исполнение (точки с работами)
Трбеуется:
    Распределить задачи между исполнителями так, чтобы было затрачено наименьшее количество ресурсов.

Под ресурсами подразумеваться может что угодно. Конкретно в этом проекте в роли ресурсов выступает 
выполнение всех заявок наименьшим количеством персонала: учитывается количество
уникальных исполнителей, которым назначена хотя бы одна заявка;пробег по маршруту каждого исполнителя: расстояние отображается по каждому исполнителю отдельно и суммарно по всему плану.
При этом имеется ограничение: не должен быть нарушен режим работы. Если для исполнителя режим работы, условно, установлен с 8:00 до 20:00, т.е. длительность всего рабочего дня составляет 12 часов, то исполняемые задачи должны уложится в этот временной диапазон.
Еще одним важным условием задачи является тот факт, что все исполнители начинают из разных контрольных точках. При этом возможно появление срочной задачи на исполнение требующее немедленное перестроение маршрутов исполнителей.

### Входные данные
На вход программному обеспечению подается файлы конфигурации (data/instances*.json и data/request*.json). В этих файлах содержится информация об исполнителях задач и самих задачах.
Входные данные обрабатываются функциональными компонентами системы:

Компонента request_listener
Модуль-приёмник пользовательских запросов. Является входной точкой обработки данных.

Компонента converter
Модуль конвертации входных данных в форматы, требуемые для дальнейшей обработки.

Компонента database_query

Модуль формирования и выполнения запросов к базе данных в зависимости от типа пользовательского запроса.

####В результате работы компонент формируются внутренние сообщения различных типов:

Сообщения типа list_instances
Сообщение содержит список всех исполнителей.

Сообщения типа user_request
Этот тип описывает запросы, отправляемые пользователем.

Сообщения типа list_tasks
Содержит информацию о всех задачах.

Сообщения типа time_table
Сообщение содержит информацию о времени в пути от точки A до точки B в виде таблицы. Таблица может корректироваться в соответствии с текущей дорожной ситуацией.

### Выходные данные
По окончании распределения задач будет сформирован файл SOLUTION.JSON, в котором будет содержаться список маршрутов для исполнителей.

## Сборка и запуск проекта
Для сборки проекта достаточно выполнить: (предполагается, что проект склонирован в директорию LCT2026_task_distribution)

```bash
cd LCT2026_task_distribution && docker build -t LCT2026_task_distribution .
```

В результате будет произведена сборка docker-image, при помощи которого может быть запущено программное обеспечению (ПО) командой:

```bash
docker run LCT2026_task_distribution
```

В результате программа изначально считывает данные из конфигурационных файлов. Файл, содержащий относительные расстояния между задачами, может занимать достаточно большое количество. Поэтому для его чтения будет произведено распараллеливание. Каждый поток будет читать батчи из файла и формаировать базу данных. Для каждой исполняемой задачи будет сформирована таблица с индексами другим задач и соответствующими дистанциями.
Важно! В данном случае дистанция измеряется в секундах (длительность пермещения из пункта А в пункт В).

После чтения файлов конфигурации начинает выполняться алгоритм имитации отжига.

### Инициализация
Инициализируется начальное состояние. По методу выбора ближнего формируется список выполняемых задач (для каждой текущей задачи выбирается ближайшая по длительности перемещения). Полученный список как раз и является трэком для исполнителя. Данный трэк заполняется до тех пор, пока время обработки всех указываемых задач укладывается в рабочее время. Затем для следующего исполнителя формируется трэк. Заполнение трэками выполняется до тех пор, пока либо не будут распределены все задачи, либо рабочее время для всех исполнителей будет заполнено. В результате будет сформировано два списка: распределенные задачи и нераспределенные. А так же будет получено первое решение, которое принимаем за лучшее. Стоит отметить, что если длительность перемещения от задачи А к задаче В равна нулю, то считается, что расстояние бесконечно долгое.

### Поиск наилучшего решения.

Поиск наилучшего решения осуществляеться двумя компонентами: task_distribution и vroom_problem_solver.
Примечание. Логика модуля task_distribution и модуля vroom_problem_solver тесно связана: task_distribution управляет общей логикой и приоритетами, а модуль vroom_problem_solver выполняет непосредственную оптимизацию маршрутов и назначений.

####Компонента task_distribution

Основной модуль распределения задач. Реализует логику назначения задач исполнителям с учётом ограничений и приоритетов, а также поддерживает динамическое переназначение при поступлении срочных задач.

Учитываемые параметры при распределении:
- стартовое положение всех исполнителей (мультидепо);
- временные окна выполнения задач;
- типы задач;
- компетенции (навыки) исполнителей;
- тип транспортного средства исполнителя.

Особенности работы:
- при поступлении задач высшего приоритета (например, аварийная заявка) модуль может переназначить текущие задачи;
- переназначение производится с учётом текущего положения исполнителя и статуса текущих работ.

####Компонента решения задачи о назначениях vroom_problem_solver (на базе библиотеки VROOM)

Модуль, реализующий оптимизационное решение задачи маршрутизации и назначения с использованием библиотеки VROOM.

Учитываемые факторы при построении оптимального плана:
- тип транспортного средства каждого исполнителя;
- компетенции исполнителей;
- временные окна исполнения задач;
- стартовые позиции всех исполнителей (поддержка мультидепо);
- длительность выполнения каждой задачи.

#Метрики //Копипаст

Metrics — агрегированные показатели решения VRP.
Все значения вычисляются один раз после solve() и служат для отчётности: сколько задач выполнено, как загружены рабочие, были ли опоздания и т.д.

Единицы измерения:
- Время: секунды (UserDuration в VROOM)
- Расстояние: метры
- Проценты/доли: не хранятся, считаются при выводе

Метрика содержит:
- Задачи
    - Общее число задач в исходной постановке (NUM_TASKS) (Нужно для контроля: должно совпадать с размером task_skills);
    - Сколько задач реально попало в маршруты ;(tasks_total − tasks_unassigned);
    - Сколько задач VROOM не смог распределить (Если > 0 — часть заказов осталась без исполнителя);
- Рабочие 
    - Сколько ТС реально выехало хотя бы к одной задаче (Считаем только маршруты с jobs > 0 — пустые не учитываем. Ключевая метрика, если цель — минимизировать число машин.)
- Суммарные времена
    - Суммарная длительность всех маршрутов (сек) (Для каждого ТС: от старта до завершения последней задачи (включает время в пути + ожидание + обслуживание))
    - Суммарное время обслуживания задач (сек) (Это "полезная" работа — то, ради чего всё затевается.)
    - Суммарное время ожидания до открытия окон (сек) (Возникает, когда рабочий приехал раньше ready_time. Потери, которых хотелось бы избежать.)
    - Суммарное время в пути (сек) (Считается как total_duration − total_service − total_waiting. Дорога — неизбежные издержки)
- Пробег
    Суммарный пробег всех маршрутов (метры). (формат long long — на случай миллионов метров. Заполняется только если у ТС есть геометрия/расстояние)
- Балансировка загрузки (Показывают, насколько равномерно распределена работа между исполнителями. Идеал: max ≈ min, std ≈ 0. На практике небольшой разброс допустим.)
    - Средняя загрузка рабочего (сек) (= total_duration / workers_used)
    - Загрузка самого занятого рабочего (сек) (Если > длительности смены — задача перегружена)
    - Загрузка самого свободного рабочего (сек) (Сравнение с max_load показывает разброс)
    - Стандартное отклонение загрузки (сек) (Чем меньше, тем лучше баланс. Считается по всем маршрутам в sol.routes)
- Качество обслуживания
    - Число задач, завершённых позже due_time (жёсткие окна) (Для VRPTW это индикатор проблем — должно быть 0)
    - Суммарная величина опозданий (сек) (Показывает, насколько сильно промахнулись.Расчет: = Σ max(0, finish_time − due_time) по всем задачам)
                                 
    

#Метрики (VRP-отчётность) //с ИИ

Метрики — агрегированные показатели решения задачи маршрутизации (VRP), вычисляемые однократно после вызова solve(). Используются для отчётности, контроля качества плана и анализа узких мест (загрузка, опоздания, баланс нагрузки).

Единицы измерения:

Время — в секундах (соответствует UserDuration в VROOM).
Расстояние — в метрах.
Проценты и доли не хранятся в метриках, рассчитываются при выводе.

##Метрики по задачам:

NUM_TASKS — общее число задач в исходной постановке. Нужно для контроля целостности: значение должно совпадать с размером task_skills.
tasks_assigned — число задач, реально попавших в маршруты. Рассчитывается как tasks_total − tasks_unassigned.
tasks_unassigned — число задач, которые VROOM не смог распределить. Если значение больше нуля, часть заказов осталась без исполнителя — стоит проверить ограничения, временные окна, компетенции или рассмотреть добавление ресурсов.

##Метрики по исполнителям

vehicles_used — число исполнителей, реально выехавших хотя бы к одной задаче. Учитываются только маршруты с jobs > 0 (пустые маршруты не считаются). Это ключевая метрика, если цель оптимизации — минимизировать количество задействованных машин.

##Суммарные временные метрики

total_duration — суммарная длительность всех маршрутов в секундах. Для каждого ТС это время от старта до завершения последней задачи, включая путь, ожидание и обслуживание.
total_service — суммарное время обслуживания задач в секундах. Это «полезная» работа — то, ради чего формируется план.
total_waiting — суммарное время ожидания до открытия временных окон в секундах. Возникает, когда исполнитель приезжает раньше ready_time. Такие задержки — потери, которых желательно избегать.
total_driving — суммарное время в пути в секундах. Рассчитывается по формуле: total_duration − total_service − total_waiting. Отражает неизбежные транспортные издержки.

##Пробег

total_distance — суммарный пробег всех маршрутов в метрах. Хранится в типе long long — это нужно, чтобы корректно учитывать большие значения (вплоть до миллионов метров). Поле заполняется только при наличии геометрии/расстояний для транспортных средств.

##Балансировка загрузки

Эти метрики показывают, насколько равномерно распределена работа между исполнителями. В идеале значения max и min должны быть близки, а стандартное отклонение — стремиться к нулю. На практике небольшой разброс считается допустимым.

avg_load — средняя загрузка рабочего в секундах. Вычисляется как total_duration / vehicles_used.
max_load — загрузка самого занятого рабочего в секундах. Если значение превышает длительность смены, значит, исполнитель перегружен.
min_load — загрузка самого свободного рабочего в секундах. Сравнение этого показателя с max_load помогает оценить разброс нагрузки между исполнителями.
std_load — стандартное отклонение загрузки в секундах. Чем меньше значение, тем лучше сбалансирован план. Рассчитывается по всем маршрутам в sol.routes.

##Качество обслуживания

Критические метрики для контроля соблюдения временных окон.

late_tasks_count — количество задач, завершённых позже due_time (жёсткие окна). Для задач типа VRPTW это значение должно стремиться к нулю.
total_lateness — суммарная величина опозданий в секундах. Рассчитывается как сумма max(0, finish_time − due_time) по всем задачам. Показывает масштаб проблемы, если опоздания всё же возникли.

###Как использовать эти метрики
Контроль качества плана. В первую очередь проверяйте tasks_unassigned > 0 и late_tasks_count > 0: эти показатели — основные сигналы о проблемах в сформированном плане.
Оптимизация парка ТС. Ориентируйтесь на vehicles_used, если одна из целей — минимизировать число задействованных транспортных средств.
Баланс нагрузки. Следите за std_load, а также сравнивайте max_load с длительностью смены: это поможет вовремя заметить перегрузку отдельных исполнителей.
Анализ издержек. Метрики total_driving и total_waiting позволяют понять, где теряются ресурсы: в дороге или из‑за простоев в ожидании открытия окон.
