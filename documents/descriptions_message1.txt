# Описание внутренних сообщений системы

##Сообщения типа list_instances

Сообщение содержит список всех исполнителей.
Формируется:
- модулем обращения к базе данных — при поступлении запроса на получение списка исполнителей;
- конвертером — при обновлении базы данных.
Примечание. Модуль обращения к базе данных формирует список доступных исполнителей задач.

Каждому исполнителю назначается определённое количество задач. В результате формируется список задач на исполнение.

Структура описания исполнителя
Для каждого исполнителя в базе хранится следующая информация:
- идентификатор исполнителя;
- имя исполнителя;
- регион обработки задач;
- байт компетентности;
- метка статуса работ:
	- статус неизвестен;
	- исполнитель недоступен;
	- исполнитель выполняет задачу;
	- исполнитель не имеет назначенных задач;
- тип перемещения:
	- тип неизвестен;
	- пешеход;
	- велосипед;
	- мотоцикл;
	- автомобиль;
	- общественный транспорт;
- текущее положение исполнителя.

##Сообщения типа user_request

Этот тип описывает запросы, отправляемые пользователем. К ним относятся:
- регистрация новых исполнителей;
- новые заявки (массив заявок);
- срочная заявка (например, авария);
- отмена заявки;
- получение текущего списка исполнителей;
- получение данных о текущих выполняемых задачах;
- получение данных о неназначенных задачах;
- и т. д.

Контейнер регистрирует сообщение типа user_request, содержащее:
- тип запроса:
	- тип  не известен;
	- обновить базу данных;
		- тип неизвестен;
		- добавить новых исполнителей задач;
		- удалить исполнительных задач;
		- заблокировать исполнителей задач;
	- обработать данные (сформировать расписание);
		 -тип неизвестен;
		- распределить задачи между исполнителями;
		- перераспределить задачи, срочная заявка;
		- перераспределить задачи, заявка отменена;
	- тип запроса: обработать данные (сформировать расписание);
		- тип неизвестен;
		- распределить задачи между исполнителями;
		- перераспределить задачи, срочная заявка;
		- перераспределить задачи, заявка отменена;
	- получить информацию из базы данных:
		- тип неизвестен;
		- получение всех свободных исполнителей задач;
		- получение всех занятых исполнителей задач;
		- получение всех не назнченных задач;
		- получение всех задач в обработке;
		- получение всех выполненных задач;
		- текущее положение всех исполнителей.

##Сообщения типа list_tasks

Сообщение формируется:
- модулем обращения к базе данных — при поступлении запросов на получение информации о задачах;
- модулем конвертации данных — при поступлении новых заявок на обработку.

Содержит информацию о всех задачах, которые:
- выполнены (из базы данных);
- не выполнены (из базы данных);
- требуют выполнения (конвертация, поступают из frontend);
- назначены (из базы данных);
- и т. д.

Контейнер регистрирует сообщение типа list_tasks, содержащее:
- список задач на исполнение;
- описание выполняемой задачи:
- уникальный идентификатор задачи:
	- тип задачи;
	- положение задачи на карте;
	- временное окно выполнения;
	- регион выполнения задачи;
- метки задач (с приоритетами):
	- тип задачи неизвестен;
	- «авария» — наивысший приоритет;
	- «подключение» — средний приоритет;
	- «локальная заявка» (ремонт / дозаказ) — наименьший приоритет.

##Сообщения типа time_table

Сообщение содержит информацию о времени в пути от точки A до точки B в виде таблицы. Таблица может корректироваться в соответствии с текущей дорожной ситуацией.
Важно. При больших объёмах данных (несколько тысяч задач) хранение таблицы в памяти может привести к заполнению ОЗУ. В этом случае следует обращаться к временной таблице через запросы к базе данных.

Контейнер регистрирует сообщение типа time_table, содержащее таблицу.

#Описание функциональных компонент системы

##Компонента request_listener

Модуль-приёмник пользовательских запросов. Является входной точкой обработки данных.

Функции:
- принимает входящие запросы от пользователя;
- формирует соответствующее внутреннее сообщение для передачи остальным модулям системы.

##Компонента converter

Модуль конвертации входных данных в форматы, требуемые для дальнейшей обработки.

Преобразует данные в следующие структуры:
- список задач на обработку;
- временная матрица путей (матрица времени в пути между точками).

##Компонента database_query

Модуль формирования и выполнения запросов к базе данных в зависимости от типа пользовательского запроса.

Поддерживаемые типы запросов и формируемые данные:
- описание всех исполнителей задач;
- описание доступных исполнителей задач;
- описание всех задач на обработку;
- описание выполненных задач;
- описание невыполненных задач;
- описание задач, выполняемых на текущий момент времени;
- иные выборки по требованию (и т. д.).

##Компонента task_distribution

Основной модуль распределения задач. Реализует логику назначения задач исполнителям с учётом ограничений и приоритетов, а также поддерживает динамическое переназначение при поступлении срочных задач.

Учитываемые параметры при распределении:
- стартовое положение всех исполнителей (мультидепо);
- временные окна выполнения задач;
- типы задач;
- компетенции (навыки) исполнителей;
- тип транспортного средства исполнителя.

Особенности работы:
- при поступлении задач высшего приоритета (например, аварийная заявка) модуль может переназначить текущие задачи;
- переназначение производится с учётом текущего положения исполнителя и статуса текущих работ.

##Компонента решения задачи о назначениях vroom_problem_solver (на базе библиотеки VROOM)

Модуль, реализующий оптимизационное решение задачи маршрутизации и назначения с использованием библиотеки VROOM.

Учитываемые факторы при построении оптимального плана:
- тип транспортного средства каждого исполнителя;
- компетенции исполнителей;
- временные окна исполнения задач;
- стартовые позиции всех исполнителей (поддержка мультидепо);
- длительность выполнения каждой задачи.

Примечание. Логика модуля task_distribution и модуля vroom_problem_solver тесно связана: task_distribution управляет общей логикой и приоритетами, а модуль vroom_problem_solver выполняет непосредственную оптимизацию маршрутов и назначений.
